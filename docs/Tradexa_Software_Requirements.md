# TRADEXA — Software Requirements & Development Specification

## 1. Project Overview

**Product name:** Tradexa

Tradexa is a web and mobile investment/trading platform designed to allow users to create accounts, fund investment accounts, monitor portfolio performance, and eventually have trading strategies execute trades on their behalf.

The project will be developed in phases.

### Phase 1 — Test/MVP

The real AI trading engine will **not** be implemented yet.

The platform will support controlled real-payment testing, but any return credited during this phase must be explicitly identified in the UI, records, and terms as a **test/simulation credit** rather than representing actual trading profit or a guaranteed investment return.

For development/testing, the system should support a configurable simulated return rate. The initial test configuration is:

> **2% per 24-hour test period**

The rate must be configurable from the admin settings rather than hard-coded throughout the application.

The production investment version must not promise a fixed return. Actual trading performance should be represented as profit or loss generated by the eventual trading strategy.

# 3. Important Financial Safety Requirement

The system must clearly distinguish between:

1. **Customer money**
2. **Available balance**
3. **Investment principal**
4. **Actual trading profit/loss**
5. **Promotional/test/simulation credits**

During Phase 1, the 2% calculation is a **test simulation**.

Do not represent simulated credits as profits generated by an AI trading system.

Do not advertise the 2% daily test rate as a guaranteed real-world investment return.

Before accepting customer money for actual investment/trading, Tradexa must obtain appropriate legal, regulatory, payment-provider, KYC/AML, consumer-protection, tax, and data-protection guidance for every jurisdiction in which it operates.

# 9. Payment Flow

A deposit must NOT immediately become confirmed simply because the frontend says payment succeeded.

Recommended flow:

```text
User chooses Deposit
        |
        v
Backend creates payment transaction
        |
        v
Payment provider checkout/payment request
        |
        v
User completes payment
        |
        v
Provider webhook/callback
        |
        v
Backend verifies payment
        |
        v
Payment marked successful
        |
        v
Ledger records deposit
        |
        v
Investment/account balance updated
```

The backend must be the authority for payment status.

Never trust a client-side success message as proof of payment.

# 11. Transaction Ledger

The ledger is one of the most important parts of Tradexa.

Do not rely only on:

```text
users.balance
```

as the financial source of truth.

Instead, every financial event should create an immutable ledger entry.

Examples:

```text
Deposit                 +$1,000.00
Test credit                +$20.00
Test credit                +$20.00
Withdrawal               -$100.00
```

The system should be able to reconstruct and reconcile a user's balance from ledger entries.

Each entry should include:

```text
ledger_entry_id
user_id
account_id
transaction_id
entry_type
amount
currency
direction
balance_after
description
created_at
reference
```

Ledger records should not be silently edited or deleted.

Corrections should create new adjustment/reversal entries.

# 12. Test Return Engine

The Phase 1 return engine is a simulation.

The initial configurable rate is:

```text
2% per completed 24-hour period
```

The calculation should be based on the defined test principal/rules and must not repeatedly compound merely because the user opens the dashboard.

Example:

```text
Initial test deposit: $1,000
Configured test rate: 2%
Completed period: 24 hours

Test credit:
$1,000 × 0.02 = $20
```

The system should create one test-credit event for each eligible completed period.

## Critical requirements

The calculation engine must:

- Use server-side timestamps
- Use UTC internally
- Prevent duplicate credits
- Be idempotent
- Handle server restarts
- Handle missed jobs
- Record every calculation
- Support reversals/corrections through ledger entries
- Never calculate based on client-side time
- Never credit twice for the same period

A scheduled worker/queue should perform calculations.

- Encrypted backups
- TLS connections
- Strong credentials
- Least-privilege database users

# 29. Encryption

Use industry-standard encryption.

For data transmitted over networks:

```text
TLS 1.2+
```

Prefer TLS 1.3 where supported.

For application-level sensitive data, use authenticated encryption such as:

```text
AES-256-GCM
```

or an approved modern equivalent.

Encryption keys must be stored separately from encrypted data.

Never implement custom encryption algorithms.

# 32. Paper Trading Before Live AI

Before connecting real funds to an AI strategy:

1. Backtest
2. Run historical simulations
3. Run paper trading
4. Monitor performance
5. Stress test
6. Validate risk controls
7. Conduct security testing
8. Conduct legal/compliance review
9. Only then consider controlled live trading

The system should support paper trading as a separate mode.

# 43. Definition of Done for Phase 1

Phase 1 is complete when:

- A user can register
- A user can securely log in
- A user can complete the required test-account verification
- A user can initiate a real payment through the configured payment provider for the controlled test
- The backend verifies the payment
- A successful payment creates a ledger deposit
- The deposit appears on the dashboard
- The configurable test rate is applied after a completed 24-hour period
- A test-credit ledger entry is created
- The same test period cannot be credited twice
- The user can view transaction history
- The user can submit a withdrawal request where enabled
- Admin can review users
- Admin can review deposits
- Admin can review withdrawals
- Admin can suspend/reactivate accounts
- Admin adjustments create ledger and audit records
- Admin actions are logged
- Users can contact support
- The website and mobile app use the same backend/database
- Sensitive data is protected
- Automated tests cover financial/accounting logic
- Backups are configured
- Production secrets are separated from development
- Payment webhooks are verified and idempotent

# 45. Key Principle

**The backend is the source of truth.**

The frontend must never be trusted to:

- Set balances
- Confirm payments
- Calculate financial balances
- Confirm withdrawals
- Modify ledger entries
- Change investment returns
- Grant admin permissions

All financial/accounting operations must be validated and executed server-side.

The database ledger, verified payment events, and audited backend operations should form the authoritative financial record for Tradexa.
